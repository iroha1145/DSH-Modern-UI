# 正文折叠修复的审计复核（2026-10-29）

Gemini 对 main `9c94369`（PR #12）的审计报告（`DSH-Modern-UI-Answer-Fold-Audit-2026-10-28.md`，不在仓库里）逐条核对的结论。规则本身见 [ui-chat-takeover.md](ui-chat-takeover.md) 末节。

## 用真实会话量过

本机 59 份、服务器 58 份会话日志里共 199 个正常结束的回合，统计「最长那条回复（≥500 字）会不会被折进过程」：

| 规则 | 服务器（86 回合） | 本机（113 回合） |
| --- | --- | --- |
| 官方 rc.4：只认最后一步 | 5 | 1 |
| PR #12：末尾连续无工具步骤里第一条回复 | 1 | 1 |
| 现在：最早的收尾回复，没有就退回最后一条回复 | 0 | 1 |

PR #12 漏掉的那 1 例正是审计的场景 1：正文在第 49 步（7227 字、无工具），10 条子代理消息让模型又做了 5 步工具调用，第 55 步写了 334 字收尾。现在的规则在插件自己的会话数据层上跑这 199 个回合，答案步与上表规则逐一相同；其中 3 个回合用到「退回最后一条回复」（之前整轮折叠），9 个回合会显示不止一条回复（多为正文加一两句收尾，有 1 例是正文前多出一句 69 字的等待说明）。本机剩下的 1 例是子代理把 3348 字正文和 `report` 交付调用放在同一步、最后一步再补一句：只有按工具名特判才能区分它和普通旁白，没有做。

## 逐条结论

| 审计条目 | 结论 | 处理 |
| --- | --- | --- |
| 场景 1：正文之后的补充步骤带工具调用，正文仍被折叠 | 成立，服务器上真实发生过 1 次 | 答案改为最早的收尾回复 |
| 场景 2：正文与收尾工具同一步、最后一步只有思考，整轮零正文 | 成立（之前官方与 PR #12 都如此），两边会话里没出现过 | 已结束回合退回最后一条回复；最后一步若还有一句文字仍会折叠正文，见上文 |
| 衍生 1：答案之后的 context 节点不算过程，两段正文之间多一个分组条 | 不成立 | `ChatGroupSeat` 在回合折叠时隐藏该回合所有步骤分组，context 节点在分组里一起隐藏；展开后它出现在原位置是正确的 |
| 衍生 2：答案锚点之后的节点不计入，控件可能被禁用而分组已隐藏 | 成立（答案之前没有任何过程时） | `turn-process-presentation.ts` 改用 `isAnswerStep` 判断，不再跳过锚点之后的节点 |
| 衍生 3：思考行三层同时隐藏 | 不是缺陷，官方 rc.4 同样如此 | 顺手加了 `groupPart !== 'reasoning'` |
| 衍生 4：复制只复制收尾、产出文件提及只给收尾、导航预览是收尾 | 成立（早于 PR #12 就是这样，正文可见后才显出来）。「文件路径全部无法点击」不准确：普通文件链接不受影响，受影响的是 deliverables 插件给本回合产出文件加的预览按钮 | 三处都改为覆盖整个答案 |
| 衍生 5：CI 没有 push 到 main 的触发；tests 被删 | 触发器自 PR #5 起就没有，部署一直用 PR 的 CI 产物（与合并后内容相同）；删测试是维护者在 `00c143e` 的决定 | 不改 |

审计给出的 `latestAnswer` 补丁没有采用：它从第 0 步正向找第一条无工具回复，遇到答案之后的步骤就停，与上面量过的规则不同。
